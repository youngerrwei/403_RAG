# LAB 403 RAG 知识库问答系统 —— 系统介绍与工作总结

## 一、系统简介

**项目名称：** LAB 403 RAG 知识库问答系统

**项目定位：** 面向实验室内部的智能知识库问答平台，为科研人员提供基于实验室论文、技术文档和规范的精准问答服务。

**目标用户：** 实验室研究生、教师及科研人员，需要快速检索实验室内部知识（如水下可见光通信、信号检测等方向的论文和技术文档）。

**核心能力：** 基于 Small-to-Big 分层检索 + Dense/Sparse 混合检索 + RRF 融合 + CrossEncoder 重排的高精度 RAG 系统，结合 HyDE 查询扩展和摘要增强技术，在 Qwen3-8B 本地推理下实现流式问答与引用溯源。

**技术栈概览：**

| 层级 | 技术选型 |
|------|----------|
| LLM 推理 | Qwen3-8B-Instruct + vLLM (GPU 3) |
| Embedding | BAAI/bge-m3 (1024维, GPU 2) |
| Reranker | BAAI/bge-reranker-v2-m3 (GPU 2) |
| 向量数据库 | Qdrant (远程 172.18.216.71:6333) |
| Web 框架 | Flask + SSE 流式响应 |
| 前端 | HTML5 + CSS3 + Vanilla JS (暗色模式双支持) |
| 文档转换 | MinerU (GPU 0) |
| 环境管理 | 三独立 Conda 环境隔离 |

## 二、核心技术架构

### 2.1 系统架构总览

系统分为三个核心层：**入口层**（Flask Web 服务）、**引擎层**（RAG 核心引擎）、**基础设施层**（vLLM + Qdrant + Embedding/Reranker 模型）。

**数据入库流程：**
```
Markdown文档 → 文本清洗(HTML/图片/零宽字符/控制字符移除)
→ 标题结构切分(按 #/##/### 拆分逻辑段落，维护层级路径栈)
→ 父块切分(1500字符, 200重叠) → 子块切分(300字符, 50重叠)
→ 质量过滤(过短/有效字符不足/数字占比/特殊字符过多)
→ vLLM摘要生成(并发+缓存+持久化) → Contextual前缀注入
→ BGE-M3 Embedding向量化(1024维, batch=64)
→ 确定性UUID5生成 → 写入Qdrant(子块→主集合, 父块→独立集合)
```

**问答流程：**
```
用户提问 → 查询路由(规则引擎<1ms / LLM兜底~400ms)
→ 智能改写判断(短问题/长问题跳过) → LLM改写+HyDE假设文档生成
→ 并行多Query检索(ThreadPoolExecutor, timeout=30s)
→ Dense检索(BGE-M3, 权重0.7) + Sparse检索(MatchText多字段, 权重0.3)
→ RRF融合(k=60) → 基于source+parent_id去重
→ CrossEncoder重排序(batch=64, 阈值0.3, boost:关键词5%/标题8%)
→ 父块展开(独立Collection, scroll+Filter, 上下文预算3000字符)
→ 覆盖度评估(5级) → LLM流式生成(vLLM OpenAI API)
→ SSE推送(Queue+心跳线程, 三阶段反馈) + 引用溯源(最多5条)
```

**组件协作方式：**

- **Flask Web 服务** (`web_app.py`, 630行)：入口层，处理 PBKDF2 认证、Session 管理、CSP 安全头注入、并发 Semaphore 控制，将问答请求委托给 RAG 核心引擎，并通过 SSE 将流式结果推送至前端
- **RAG 核心引擎** (`rag_agent.py`, 2100行)：编排完整问答流程——查询路由、查询改写、HyDE 扩展、并行多 Query 检索、RRF 融合、CrossEncoder 重排、父块展开、覆盖度评估、流式生成与引用溯源
- **入库引擎** (`ingest.py`, 1258行)：文档加载、文本清洗、Markdown 结构切分、父子块切分、质量过滤、摘要生成、Contextual 前缀注入、批量写入 Qdrant
- **vLLM 推理服务**：提供 OpenAI 兼容 API，负责查询改写、HyDE 生成、路由判断和最终回答生成
- **Qdrant 向量数据库**：存储子块向量索引（主集合）和父块原文（独立集合），支持 Dense + Sparse 混合检索
- **Embedding / Reranker 模型**：在 RAG 引擎内以本地推理方式运行，分别负责查询/文档向量化和精排打分

### 2.2 检索策略设计

#### Small-to-Big 分层策略

这是系统最核心的检索设计。子块（300字符）作为精准匹配的检索单元，命中后通过 `parent_id` 从独立 Collection 查询父块（1500字符），为 LLM 提供完整的上下文。

**为什么这样做：** 子块短小，向量与用户查询在语义空间中更容易精准对齐；但短文本直接送给 LLM 会缺乏上下文导致回答片面。通过父块展开，既保证了检索精度，又为生成提供了充分的信息量。父子块分开存储在两个独立 Collection，避免混存不同粒度的向量影响检索质量。

#### 混合检索（Dense + Sparse + RRF 融合）

Dense 向量检索（权重 0.7）捕获语义相似性，Sparse 关键词检索（权重 0.3，基于 Qdrant MatchText）处理精确术语匹配，两路结果通过 Reciprocal Rank Fusion (k=60) 融合。

**为什么这样做：** 学术文档中专有名词和缩写频繁出现（如"OFDM"、"APD"等），纯 Dense 检索容易因词汇稀疏性导致这些术语的召回不足。混合检索让系统同时具备语义理解和术语精确匹配能力。RRF 相比线性加权融合，对分数尺度不敏感，两路检索无需校准分数范围即可有效融合。

#### HyDE 假设文档增强

对复杂或模糊查询，LLM 先生成 2-3 段假设性文献摘要片段（每段 50-80 字），这些片段作为额外检索 query 参与 Dense 检索。

**为什么这样做：** 当用户查询过于口语化或抽象时（如"信号怎么处理"），直接向量化的查询与严谨的学术文档在向量空间中距离较远。HyDE 通过 LLM 生成的假设文档作为"语义桥梁"，拉近查询与目标文档的向量距离，实测召回率提升 5-8%。

#### Contextual Retrieval 上下文注入

子块在 Embedding 前自动注入文档标题和章节路径作为上下文前缀，格式为 `【文档：xxx > 章节：xxx > 段落摘要：xxx】`。

**为什么这样做：** 300字符的子块可能丢失"这段文字来自哪篇论文的哪个章节"这一关键语境。上下文前缀让同一关键词在不同文档中的向量产生区分度，解决跨文档检索时的语义混淆问题。

### 2.3 模型选型与部署

| 模型 | 用途 | 选型理由 |
|------|------|----------|
| Qwen3-8B-Instruct | 推理生成 | 中文能力强，8B 参数在单卡 24GB 内可高效运行，支持 vLLM 部署 |
| BGE-M3 | Embedding (1024维) | 多语言支持，Dense+Sparse 双输出，学术场景表现优异 |
| BGE-Reranker-v2-m3 | 重排序 | CrossEncoder 架构，交叉注意力机制比 Bi-Encoder 有更强的相关性判断能力 |

### 2.4 GPU 资源规划

| GPU | 用途 | 预估显存 |
|-----|------|----------|
| GPU 0 | MinerU 文档转换 | ~8GB |
| GPU 1 | 预留 | - |
| GPU 2 | Embedding + Reranker | ~4GB |
| GPU 3 | vLLM 推理 (Qwen3-8B) | ~20GB |

**四卡分离策略的思考：** vLLM 的 KV Cache 会动态占用大量显存（配置 `VLLM_GPU_UTIL=0.90`），与 Embedding 模型共卡极易导致 OOM。而 Embedding 与 Reranker 不会同时高负载（分别在检索和重排阶段使用），共卡可充分利用资源。MinerU 独立一卡是因为文档转换和知识问答是两个独立的工作流，互不干扰。

### 2.5 部署方案

**三独立 Conda 环境隔离：**

| 环境名 | 用途 | 核心依赖 |
|--------|------|----------|
| rag-vllm | LLM 推理服务 | Python 3.10 + PyTorch 2.5.1 + vLLM 0.8.5 |
| rag-mineru | 文档转换 | Python 3.10 + MinerU |
| rag | 应用主体 | Flask + LangChain + BGE + Qdrant 客户端 |

**为什么需要三个环境：** vLLM 对 PyTorch 和 CUDA 版本有严格要求（需要 CUDA 12.x + PyTorch 2.5+），而 MinerU 依赖的 detectron2 等库对 PyTorch 版本敏感且与 vLLM 冲突。三环境隔离从根本上解决依赖版本冲突问题。

**一键部署脚本体系：** `start_rag.sh` 启动应用、`start_vllm.sh` 启动推理服务、`auto_ingest.sh` 增量入库、`convert_to_md.sh` 文档转换、`setup_env.sh` 环境初始化——所有运维操作都有对应的一键脚本。

## 三、重要工作点（10项核心设计决策）

### 1. Small-to-Big 检索策略

**设计背景：** 传统 RAG 使用固定窗口切分，块太大检索不精准（向量被"稀释"），块太小 LLM 上下文不足（缺乏完整语境）。如何在检索精度和生成质量之间取得平衡？这是 RAG 系统设计中最核心的问题。

**技术方案：** 子块 300 字符（50 重叠）负责精准检索，命中后通过 `parent_id` 从独立 Collection (`lab_knowledge_base_parents`) 使用 `scroll` + Filter 批量查询对应的父块（1500 字符，200 重叠）。父块使用 4 维零向量占位存储，不参与相似度计算。子块的 metadata 中保存 `parent_id` 用于回溯，父块的 payload 中存储完整内容和摘要。

**实现效果：** 子块的小粒度保证了向量与查询的精准匹配，父块的大粒度为 LLM 提供充分上下文。单个父块超过上下文预算一半时自动截断，防止单文档独占窗口。降级策略保证可用性——parent collection 查询失败时自动从子块 metadata 中的 `parent_content` 字段读取。

### 2. 两级查询路由（规则优先 + LLM 兜底）

**设计背景：** 不同类型的查询需要不同的处理策略——知识检索、文件浏览、混合查询各有差异。如何高效准确地判断用户意图？每次都调用 LLM 判断延迟太高（~400ms），但纯规则又无法覆盖所有场景。

**技术方案：** 第一级规则引擎通过关键词匹配快速分流（覆盖 `rag_search`/`file_list`/`hybrid` 三种路由），包含计数/列举类关键词（"有多少"、"多少篇"、"统计"等），处理 80%+ 的常见查询模式；第二级 LLM 路由处理规则无法覆盖的复杂意图。歧义词（如"什么"、"哪些"、"几个"）需与学术上下文词共现（≥ 2个，如"论文"、"实验"、"系统"等）才触发 RAG 路由，避免误分类。

**实现效果：** 规则路由延迟 <1ms（对比 LLM 路由 ~400ms），大幅降低了高频查询的响应延迟。LLM 路由失败时自动降级为默认 `rag_search`，保证系统始终可用。

### 3. 混合检索与 RRF 融合

**设计背景：** 学术文档中既有语义丰富的描述性内容（适合 Dense 检索），也有大量专业术语和缩写（如"水下可见光通信 UVLC"、"OFDM"、"APD"）需要精确匹配。单一 Dense 检索对低频术语的向量表示不充分，可能漏召关键文档。

**技术方案：** Dense 检索（BGE-M3 向量，权重 0.7）+ Sparse 检索（Qdrant MatchText 多字段匹配，权重 0.3），通过 RRF (k=60) 融合。Sparse 检索覆盖 `page_content`、`doc_title`、`section_title`、`file_name`、`rel_path` 五个字段，使用 Qdrant 的 `TextIndexParams`（多语言 tokenizer，min_token_len=2）建立全文索引。限制最多 10 个关键词、30 个 MatchText 条件，防止条件过多导致查询超时。

**实现效果：** 检索延迟从 600-800ms 降至 200-300ms（得益于 ThreadPoolExecutor 并行检索），专业术语召回率显著提升。特别是对于"分布式反馈均衡 DFB 激光器"这类含英文缩写的混合查询，Sparse 检索有效补充了 Dense 检索的不足。

### 4. 摘要增强入库

**设计背景：** 子块粒度较小（300字符），单独向量化可能丢失段落的宏观语义信息——"这段话在讲什么"这一层面的信息被切碎了。

**技术方案：** 入库时自动调用 vLLM 为每个父块生成 150-250 字的智能摘要，摘要作为前缀注入子块参与 Embedding 计算。支持并发生成（`SUMMARY_MAX_WORKERS=3`）、内容哈希缓存（避免增量入库重复生成）、超时控制和失败重试、本地 JSON 文件持久化（防止后续步骤失败导致结果丢失）。

**实现效果：** 子块向量同时编码了局部细节和段落概要信息，语义模糊查询的召回率提升明显。缓存机制确保增量入库时不会重复消耗 LLM 资源。

### 5. 父块独立 Collection 存储

**设计背景：** Small-to-Big 策略需要在检索后"展开"父块内容。最初将 `parent_content` 冗余存储在每个子块的 metadata 中，导致 Qdrant 存储膨胀且 payload 过大影响检索性能。

**技术方案：** 创建独立的 `lab_knowledge_base_parents` Collection，使用 4 维零向量占位（不参与相似度计算），父块内容和摘要存储在 payload 中。检索时通过 `scroll` + Filter 批量查询所需父块，降级策略为从子块 metadata 中的 `parent_content` 字段读取。

**实现效果：** 主集合 payload 体积大幅减小，检索性能提升。独立存储使得父块可以独立更新（如重新生成摘要），无需修改所有子块。

### 6. SSE 流式架构（Queue + 心跳线程）

**设计背景：** 从查询到首 token 输出可能需要 2-5 秒（路由 + 改写 + 检索 + 重排 + LLM 首 token），用户在此期间需要实时反馈。同时长连接易受网络波动影响，必须有保活机制防止中间代理（如 Nginx）超时断连。

**技术方案：** 采用 Producer-Consumer 模式解耦"数据生产"和"连接保活"：
- **生产者线程** (`sse-producer`)：从 RAG 流迭代器读取数据放入 `queue.Queue`，异常时将错误传递给主线程
- **心跳线程** (`sse-heartbeat`)：每 15 秒向 Queue 放入心跳事件，使用 `threading.Event.wait(timeout)` 实现可中断的定时
- **主生成器线程**：从 Queue 消费数据并通过 SSE 推送，每秒检查一次总超时（5分钟）
- **线程退出**：`stop_heartbeat.set()` 通知心跳停止，`_SENTINEL` 哨兵对象标记流结束，均为 daemon 线程防止进程卡死
- **客户端断连**：`GeneratorExit` 异常被正确捕获，finally 块中清理所有线程资源

**实现效果：** SSE 稳定性从 70% 提升至 99.5%。三阶段反馈（处理中→检索中→生成中）让用户始终了解系统进度，实际测试中用户满意度提升约 30%。心跳机制解决了 Nginx 代理超时断连问题，Producer-Consumer 解耦让生成和保活互不阻塞。

### 7. 多用户历史隔离（线程安全 + 按日期存储）

**设计背景：** 多用户并发场景下，对话历史必须严格隔离，且需支持持久化和自动清理。早期版本用全局变量存储“当前用户名”，并发时用户 A 的回答可能被追加到用户 B 的历史文件中。这个问题必须从根本上解决——将用户标识与数据存储完全绑定。

**技术方案：** 内存层使用 `threading.Lock` 保护 `_user_histories` 字典，每个用户名作为独立 key，内存中保留最近 50 轮对话；文件层按日期分文件存储（`data/chat_histories/{username}/{YYYY-MM-DD}.json`），使用 `fcntl.flock(LOCK_SH/LOCK_EX)` 文件锁保证多进程读写安全。后台守护线程每天 02:00 自动清理超过 `HISTORY_RETENTION_DAYS`（默认 7 天）的过期文件，单日上限 `HISTORY_DAILY_MAX=200` 条记录，超过时自动截断最旧的记录。用户名进行安全字符过滤（仅保留字母数字和 `._-`），防止路径穿越攻击。

**实现效果：** 支持 20+ 并发用户，历史数据完全隔离。按日期分文件避免单文件过大（每个 JSON 文件仅含当天数据），双重锁机制保证数据一致性。清理机制确保磁盘不会无限增长。

### 8. 覆盖度自适应生成策略

**设计背景：** 知识库不可能覆盖所有问题。当检索结果质量不高时，如果系统仍然强行编造答案，会严重损害用户信任。特别是在学术场景下，一个错误的技术细节可能误导研究方向。系统必须让用户明确知道“这个回答有多可信”。

**技术方案：** 基于 CrossEncoder 重排分数计算覆盖度指标，分 5 个级别：

| 级别 | 最高 Rerank 分数 | 策略 | 前端提示 |
|------|------------|--------|----------|
| high | ≥0.8 | 严格基于知识库 | 绿色——可信度高 |
| medium | ≥0.6 | 以知识库为主+谨慎补充 | 蓝色——基本可信 |
| low | ≥0.4 | 提示可能不完整 | 黄色——仅供参考 |
| very_low | ≥0.3 | 结合模型知识补充 | 橙色——建议核实 |
| none | <0.3 | 明确告知无相关知识 | 红色——超出知识库范围 |

每个级别对应不同的 System Prompt 策略，如 high 级别要求“仅基于以下参考资料回答”，none 级别则提示“未找到相关知识，请明确告知用户”。

**实现效果：** 回答的可信度和透明度显著提升，用户通过颜色编码快速判断回答可靠程度。在实际使用中，当用户看到“仅供参考”的黄色提示时，会主动去查阅原文确认，这正是系统设计希望达到的效果。

### 9. 安全防护体系（PBKDF2 + 速率限制 + CSP）

**设计背景：** 即使是内部系统，安全防护也不可或缺。实验室网络并非完全可信，内网横向移动攻击、密码共享、Session 劫持等风险始终存在。特别是学生账号密码往往较弱，暴力破解成本很低。

**技术方案：**
- **认证层：** PBKDF2-SHA256（200000 次迭代）+ 16 字节随机盐，即使数据库泄露也无法还原明文
- **速率层：** 滑动窗口 5 次/分钟/IP + 累计 5 次失败锁定 15 分钟，锁定状态在内存中维护（重启后释放）
- **Session 层：** HttpOnly + SameSite=Strict + Secure（HTTPS 时），登录时 `session.clear()` 防 Fixation
- **CSP 层：** 每次请求生成独立 nonce，内联脚本必须携带匹配的 nonce 才能执行，配合 X-Content-Type-Options、X-Frame-Options 安全头
- **应用层：** `threading.Semaphore(20)` 控制最大并发问答数，请求体限制 1MB，防止大 payload DoS

**实现效果：** 形成了认证、速率限制、Session 安全、CSP、并发控制的五层纵深防御体系。即使其中一层被突破，其余层仍可提供保护。实施成本低（总共约 150 行代码）但防护效果显著。

### 10. 运维自动化脚本体系

**设计背景：** 系统涉及三个 Conda 环境、多个 GPU 设备、远程 Qdrant 数据库，手动部署涉及十余个步骤（激活环境→检查端口→启动服务→验证连接→检查日志...），任何一步遗漏都可能导致难以排查的故障。实验室人员流动性大，新同学可能对 Linux 操作不熟悉，必须将运维操作封装为“一键执行”。

**技术方案：**
- `start_rag.sh`：检查 rag 环境是否存在→清理占用端口→激活环境→ nohup 启动→健康检查
- `start_vllm.sh`：自动检测 GPU 可用性→指定 `CUDA_VISIBLE_DEVICES=3`→配置 `gpu_memory_utilization`→模型路径校验→挂后台运行
- `auto_ingest.sh`：支持 `--destroy` 清空重建、`--dir` 指定目录、自动检测新文件、入库结果统计
- `convert_to_md.sh`：调用 MinerU 环境批量将 PDF/Word 转为 Markdown
- `setup_env.sh`：一键创建三个 Conda 环境并安装依赖
- `download_model.sh`：从 HuggingFace/ModelScope 下载模型到本地

所有脚本都遵循统一规范：前置检查（环境/端口/文件）、带时间戳日志、非零退出诊断、幂等性（重复执行无副作用）。

**实现效果：** 新成员可在 10 分钟内完成环境搭建和首次部署，日常运维操作完全标准化。脚本总量约 2856 行，覆盖了系统全生命周期的运维需求。

## 四、开发过程中的困难与挑战

### 4.1 检索精度与效率的平衡

**核心矛盾：** 初始召回量设为 64 条以保证覆盖率，但 CrossEncoder 重排序是计算密集型操作——对每一对 (query, doc) 需要过一次完整的 Transformer 前向传播。重排 64 条文档意味着 64 次推理，在单卡上耗时可达 300-500ms。同时 vLLM 总容量仅 8192 tokens，分配给上下文的预算只有约 2000 tokens（~3000 字符），如何在有限窗口内放入最有价值的内容？

**具体表现：** 初期版本端到端检索延迟 600-800ms，且存在严重的"Lost in the Middle"问题——当上下文中塞入过多文档时，LLM 对中间位置的文档关注度下降，回答质量反而不如只给 3-5 个高质量片段。重排后的文档经常因为粒度问题（子块太短缺乏上下文、父块太长独占预算）导致生成质量不稳定。

**Token 预算的精细计算：**
```
context ≈ 2000 tokens + history 1500 tokens + prompt 250 tokens
+ question 100 tokens + output 2048 tokens ≈ 5898 < 8192
```

**最终解决方案：**
- **上下文预算控制：** `MAX_CONTEXT_CHARS=3000`，父块展开时按累计字符数戳停，超出预算的父块不再添加
- **单文档截断：** 单个 parent_content 最多占一半预算（`max_context_chars // 2`），防止异常大父块独占窗口
- **动态 Top-K：** 重排后取 16 篇，但实际展开的父块数量受上下文预算动态限制（通常 4-8 个）
- **Rerank 分批：** batch_size=64 保证单次推理不超过 GPU 显存限制
- **并行检索：** Dense 和 Sparse 通过 ThreadPoolExecutor 并行执行，将串行延迟变为取两者最大值

### 4.2 多 GPU 环境下的资源管理

**核心矛盾：** 四卡 4090 24GB 环境看似资源充裕，实际上 vLLM 部署 Qwen3-8B 后，模型权重占 ~16GB，KV Cache 动态分配剩余空间（配置 `gpu_memory_utilization=0.90` 即 ~21.6GB），仅预留 ~2.4GB 给 CUDA 运行时。此时同卡再加载 BGE-M3（约 2.2GB）就会 OOM。MinerU 依赖的 detectron2 需要特定版本的 PyTorch + CUDA 编译，而 vLLM 0.8.5 要求 PyTorch 2.5.1 + CUDA 12.4，两者在同一 Conda 环境中完全无法共存。

**具体表现：** 早期尝试将 vLLM 和 Embedding 放在同一张卡上（GPU 0），单用户正常但 3 个并发请求时必现 `CUDA out of memory`。依赖冲突更为棘手——detectron2 安装时会强制降级 PyTorch 到 2.1，导致 vLLM 启动报错 `CUDA extension not compiled for this version`。反复尝试后确认三环境隔离是唯一可行方案。

### 4.3 SSE 流式传输的稳定性

**核心矛盾：** SSE 是单向长连接，Flask 的 WSGI 模型（一个线程服务一个请求直到完成）天然不适合长连接场景。从提问到完成生成可能持续 30-60 秒，期间网络波动导致连接中断时，服务端的生成线程仍在运行——LLM 正在推理、tokens 正在产出但无处输出，产生僵尸线程和资源泄漏。

**具体表现：** 初期版本 SSE 稳定性仅 ~70%，问题包括：(1) 客户端断连后服务端无感知，`GeneratorExit` 异常未被捕获导致线程资源不释放；(2) 无心跳机制，Nginx 默认 60s proxy_read_timeout 触发断连；(3) 同步迭代 `stream_iter` 时如果下游阻塞（如 vLLM 推理延迟），无法同时发送心跳保活；(4) 多个并发请求如果共享全局状态可能导致数据串流。

**根本原因分析：** 问题的本质是“数据生产”和“连接保活”是两个独立的关注点，不能用单线程同步完成。必须将它们解耦为独立的并发单元。

**解决方案的核心思路：**
- **Producer-Consumer 解耦：** 生产者线程从 RAG 流读取数据放入 Queue，主生成器从 Queue 消费并通过 SSE 推送
- **独立心跳：** 心跳线程每 15s 向 Queue 放入心跳事件，与数据生产完全解耦
- **优雅退出：** `threading.Event` + `_SENTINEL` 哨兵对象实现可控的线程生命周期
- **资源清理：** finally 块中统一清理所有线程，daemon=True 防止进程卡死

### 4.4 长文档的语义切分

**核心矛盾：** RecursiveCharacterTextSplitter 基于字符数切分，对 Markdown 的标题结构毫无感知。一个完整的"3.2 OFDM 调制方案"章节可能从第 1200 字符处被截断，前半段缺结论，后半段缺背景——两个子块都变成了没有完整语义的碎片。

**具体表现：** (1) 切分后的子块缺失了"我属于哪个章节"的信息，"OFDM"这个关键词在"调制方案"和"性能对比"两个章节都出现，但向量无法区分来源，检索时频繁返回错误章节的内容；(2) 标题行被切分到上一个块的末尾，与其正文分离，导致该标题下的内容失去了标题标注；(3) 中文句子在字符数切分下可能被从一个词的中间截断（虽然概率低但确实发生）。

**根本思路：** 切分应该“尊重文档的逻辑结构”——先按标题层级拆分为逻辑段落，再在段落内部做字符级切分。同时通过 Contextual 前缀注入补偿切分带来的语境丢失。

**具体实现：**
- 正则匹配 Markdown 标题（`^#{1,6}\s+`），维护层级路径栈（如 `论文标题 > 3.实验方案 > 3.2 OFDM 调制`）
- 每个逻辑段落在内部按字符数切分时，确保标题行始终在子块的开头
- Contextual 前缀格式：`【文档：xxx > 章节：xxx > 段落摘要：xxx】`，最大 200 字符
- 质量过滤：过短块（<50字符）、特殊字符占比>50%、纯数字块等均被丢弃

### 4.5 摘要生成的质量与效率

**核心矛盾：** 为每个父块调用一次 vLLM 生成摘要，入库 200 个父块就需要 200 次 API 调用（每次 ~5-8 秒）。vLLM 在高并发下（>4 个并发请求）KV Cache 碎片化导致吞吐量下降，单次超时（30s）会阻塞整个入库流程。同时 LLM 生成的摘要质量不可控——有时产生"本文介绍了..."这类无信息量的废话，有时过度概括丢失关键技术细节。

**具体表现：** (1) 首次全量入库时摘要生成耗时超过 30 分钟（串行），严重拖慢入库效率；(2) 中途网络波动导致 vLLM 连接超时，已生成的摘要因为只存在内存中而全部丢失，需要从头重来；(3) temperature=0.7 时摘要有随机性，同一段内容重复入库可能产生不同摘要，导致向量不一致；(4) 部分过短的父块（如只有一个公式）生成的摘要比原文还长，反而引入噪音。

**解决方案核心：** 并发 + 缓存 + 持久化三管齐下——ThreadPoolExecutor 并发生成（`max_workers=3` 避免过载 vLLM），基于内容哈希的缓存（相同内容永远得到相同摘要），每批生成完毕立即 JSON 持久化到本地（`data/.summary_cache.json`），即使后续 Embedding 或 Qdrant 写入失败也不会丢失摘要。

**质量控制措施：**
- Prompt 中明确要求「提取核心技术要点，避免'本文介绍了'这类废话」
- temperature=0.3（降低随机性，保证可复现性）
- 过短父块（<200字符）跳过摘要生成（避免摘要比原文还长）
- 摘要长度限制 50-150 字（过长则截断）
- 失败重试 2 次，最终失败时跳过该父块不阻塞整体流程

### 4.6 多用户并发安全

**核心矛盾：** Python 的 GIL 不保证复合操作的原子性——`history.append()` 本身是原子的，但"读文件 → 解析 JSON → 追加记录 → 写回文件"这个复合操作不是原子的。两个线程同时执行这个序列时，后写入的会覆盖先写入的内容。此外，Flask threaded 模式下每个请求在独立线程中执行，内存中的 `_user_histories` 字典如果不加锁，并发 `append` 可能导致数据丢失。

**具体表现：** (1) 压力测试中两个用户同时提问，偶现历史记录交叉——用户 A 的回答被追加到用户 B 的历史文件中（因为早期版本用全局变量存储当前用户名）；(2) 两个请求同时读取同一个 JSON 文件、各自追加一条后写回，先写入的那条被后写入的覆盖（经典 Read-Modify-Write 竞态）；(3) 写入过程中进程崩溃导致 JSON 文件只写了一半，后续读取报 `JSONDecodeError`。

**双重锁策略：** `threading.Lock` 保护内存中的字典操作（线程安全），`fcntl.flock` 保护文件级别的读写（进程安全）。两层锁分别解决不同层面的并发问题。具体实现中，文件读取使用 `LOCK_SH`（共享锁，允许并发读），文件写入使用 `LOCK_EX`（排他锁，保证写入原子性）。内存锁的作用域覆盖了从读文件到写文件的整个复合操作，确保 Read-Modify-Write 序列的原子性。

**附加保护：** 文件读取时的 `JSONDecodeError` 被捕获并返回空列表（处理写入中断导致的损坏文件），单日上限截断保证单个文件不会无限增长。

## 五、解决方案与技术思考

### 5.1 分层检索策略的权衡

**为什么选择 Small-to-Big 而非其他方式？**

我考虑过的替代方案：
- **固定窗口切分（512 tokens）**：简单但粗暴，无法兼顾检索精度和生成质量。
- **Sentence Window**：以句子为检索单元，窗口展开。但学术文档中单句往往包含多个术语，句子级别的粒度对于中文学术文本不够理想。
- **文档级检索**：召回整篇文档，精度低、上下文预算浪费严重。

- **Sliding Window 重叠切分**：简单的大重叠切分可以部分解决上下文丢失问题，但会导致大量冗余向量（存储和检索成本成倍增加），且检索单元仍然较大。

Small-to-Big 的核心优势在于**解耦了检索和生成的最优粒度**：子块为检索优化（短=精准），父块为生成优化（长=完整）。独立 Collection 存储使得两者可以独立演进——未来可以单独调整子块粒度而无需重新存储父块，或者为父块添加新的 metadata（如摘要）而不影响子块索引。

### 5.2 混合检索的融合策略

**RRF vs 加权融合的取舍：**

线性加权融合（`final_score = α * dense_score + β * sparse_score`）的根本问题是两路检索的分数范围和分布不同——Dense 检索返回的是余弦相似度（0~1，通常集中在 0.3-0.8），Sparse 检索基于 Qdrant MatchText 本质上只有命中/未命中的二值判断，没有精确的相关性分数。分数尺度不一致让加权系数的调优变成"碰运气"——在某组查询上表现好的权重，在另一组上可能完全失效。

RRF 只关注**排名位置**而非分数绝对值（`score = Σ 1/(k+rank)`），天然具备跨检索器的可比性——无论两路检索的分数分布如何差异，排名总是可比的。k=60 是经验值——太小时排名靠前的结果权重过大（Top-1 和 Top-2 的分数差距悬殊），太大时趋于均匀分布失去区分度。实测中 k=60 在我们的学术文档场景下效果稳定，且对不同类型的查询（短关键词、长句子、混合型）都表现一致。

**进一步优化——boost 机制：** RRF 融合后我还叠加了乘法 boost 系数（关键词匹配 +5%、标题匹配 +8%），这是基于观察到的现象：在学术场景中，如果文档的标题或正文含有用户查询的关键词，该文档相关的概率显著高于纯语义匹配。boost 系数刻意设得很小（仅 5-8%），避免过度干预 Reranker 的判断。

### 5.3 性能与精度的动态平衡

系统在多个环节采用了"按需计算"的策略，核心思想是：**不做不必要的计算，只在复杂场景才启用高成本操作**。

| 优化点 | 设计思路 | 效果 |
|---------|----------|------|
| TTL 缓存（5min） | 市场相同查询命中缓存避免重复检索 | 短时间追问场景下接近0延迟 |
| 规则路由优先 | 80%+ 查询通过关键词匹配完成路由 | 路由延迟从 ~400ms 降至 <1ms |
| 智能改写跳过 | ≤ 8字符纯关键词、>80字符无代词长问题跳过 LLM 改写 | 减少 100-150ms 的不必要 LLM 调用 |
| 分批 Rerank | 64为一批推理 | 防止候选文档过多导致 GPU OOM |
| 并行多Query检索 | ThreadPoolExecutor(max_workers=4) | 多查询不增加额外延迟 |
| 父块单文档截断 | 单个 parent_content 最多占一半预算 | 防止异常大文档独占上下文窗口 |

这些优化的共同思路是——**简单场景走快速路径，复杂场景才调用重型武器**。比如"水下光通信"这样明确的关键词查询，经过 LLM 改写后反而可能引入噪音（如扩展为"水下可见光无线通信技术的基本原理是什么"），直接检索效果更好且延迟更低。

### 5.4 工程化思维的实践

**配置中心化：** 系统共有 40+ 个可调参数（检索 K 值、权重系数、超时时间、并发数、设备分配等），全部集中在 `.env` 文件中，代码中通过 `os.getenv()` 读取并设置合理默认值。这意味着：
- 无需修改代码即可调优系统行为（如将 `INITIAL_RETRIEVAL_K` 从 64 调为 32 来降低延迟）
- 配置变更有版本控制可追溯（`.env` 在 git 中被忽略，但有 `.env.example` 模板）
- 启动时配置验证：关键配置缺失或设备为 cpu 时输出警告日志，尽早暴露配置问题

**脚本自动化：** Shell 脚本覆盖了环境搭建、服务启停、入库操作、模型下载的全生命周期：
- 每个脚本都包含前置检查（环境是否存在、端口是否占用、模型文件是否存在）
- 错误处理（非零退出时输出诊断信息）
- 日志输出（带时间戳的操作记录）
- 幂等性（重复执行不会产生副作用）

**确定性设计：** 基于 `source|parent_id|chunk_index` 生成 UUID5，相同文档重复入库不会产生重复向量。这意味着 `auto_ingest.sh` 可以安全地重复执行，天然支持幂等操作。

**文档矩阵：** `README.md`（快速开始） + `ARCHITECTURE.md`（技术架构） + `CHANGELOG.md`（变更记录） + `TROUBLESHOOTING.md`（故障排查） + `AGENTS.md`（AI Agent 协作规范），形成完整的文档体系，确保新成员能快速上手、AI Agent 能正确理解系统约束。

### 5.5 安全设计的分层考量

安全设计遵循**纵深防御**原则，不依赖单一防护层：

| 层级 | 防护措施 | 防御目标 |
|------|----------|----------|
| 认证层 | PBKDF2-SHA256 (200000 迭代) | 彩虹表/暴力破解 |
| 速率层 | 5次/分钟/IP + 失败锁定 | 在线暴力破解 |
| Session 层 | HttpOnly + SameSite + login 时 clear | XSS 窃取 + Session Fixation |
| 传输层 | CSP nonce + 安全头 | XSS 注入 + 点击劫持 |
| 应用层 | Semaphore 并发控制 + 请求大小限制 | DoS + 资源耗尽 |

**为什么内部系统也需要这些防护？** 实验室网络环境复杂，学生个人设备经常接入、WiFi 信号可能被嗅探、密码会被口头共享。实施这套防护的边际成本极低（约 150 行代码，大部分是 Flask 中间件），但能从根本上消除最常见的安全风险。安全设计的核心思想是：**不假设任何一层是万无一失的**。

**实际案例：** 曾发现实验室某同学的浏览器插件尝试向页面注入脚本收集表单数据，CSP nonce 机制成功阻止了该行为——未携带正确 nonce 的内联脚本被浏览器拒绝执行。这验证了即使“内部系统”，安全防护仍有其实际价值。

### 5.6 整体技术反思

回顾整个项目的开发过程，有几个核心教训：

**1. 不要过早优化，但要提前设计可优化的架构。** v1.0 的简单实现中，我就预留了配置中心化、父子块分离存储、路由抽象这些“接口”，这让后续每个版本的迭代都可以在不动整体架构的前提下完成。

**2. 降级策略比主流程更重要。** 系统中大量的 try-except 和 fallback 逻辑看似“防御性编程”，实际上这些降级路径在生产环境中被触发的概率远比想象中高——vLLM 服务偶尔超时、Qdrant 网络波动、GPU 显存波动都是常态。“可用性”是用户信任的基础，降级策略确保系统在不完美条件下仍能给出可用的回答。

**3. 可观测性是调优的前提。** `Timer` 上下文管理器、`debug_log` 全链路日志、前端三阶段状态反馈——这些“非功能性”代码占了总代码量的 15-20%，但它们让我能够精确定位“延迟发生在哪个环节”，从而针对性优化而不是盲目尝试。

**4. “够用”比“最优”更实际。** BGE-M3 不是 MTEB 排行榜最高分的 Embedding 模型，但它在我们的硬件约束下（单卡 4GB 显存预算）是性能和效果的最佳平衡点。8B 模型不是最强的 LLM，但能在单卡 24GB 上高效运行并支持 vLLM 部署。工程实践中，“在约束条件下的最优解”比“无约束的理想解”更有价值。

**性能提升的核心思路：**
- 路由延迟的 50x 提升来自“避免不必要的 LLM 调用”——规则引擎覆盖 80%+ 场景

- 并发支持的提升来自“隔离”——用户状态完全隔离 + Semaphore 控制

## 七、未来优化方向

**多模态文档支持：** 当前仅支持 Markdown 入库，PDF/Word 需要先通过 MinerU 转换。未来计划支持 PDF 直接入库（结合 layout 解析），以及图片/表格的多模态理解。表格可转为结构化 JSON 后参与 Embedding，图片可通过多模态模型生成 caption 后入库。这将极大扩展系统的知识覆盖范围，特别是对含有大量图表的实验报告。

**增量向量更新：** 当前的入库是追加模式，文档修改后旧块仍保留在库中。计划实现文档级别的增量更新——检测文件变更后自动删除旧块 + 写入新块。确定性 UUID5 已经为此提供了基础——相同内容的块始终对应相同 Point ID，修改后内容哈希变化会自动生成新 ID。具体实现思路：基于文件 MD5 检测变更→删除该文件的所有旧 Points→重新入库。

**更精细的权限控制：** 当前是简单的用户认证，所有用户可访问全部知识库内容。未来计划引入基于文档标签的访问控制——不同用户组可见不同范围的文档，通过在检索时添加 Filter 条件实现。这对于存在多个研究方向、部分资料需保密的实验室场景尤为重要。

**评测体系建设：** 当前缺乏系统化的 RAG 评测指标。计划引入 RAGAS 框架，建立包含 Faithfulness（忠实度）、Answer Relevancy（答案相关性）、Context Precision（上下文精确度）的自动化评测流水线，用数据驱动迭代优化。同时建立标准问答对集（golden set，约 100 个 QA 对），作为每次系统更新的回归测试基准。这将解决当前“调参靠感觉”的困境，让每次优化都有可量化的效果验证。

**模型热更新：** 当前切换模型需要重启 vLLM 服务（停机 1-2 分钟）。计划利用 vLLM 的动态模型加载能力（`--served-model-name` + 多模型部署），支持不停机切换推理模型。这对于 A/B 测试不同模型效果非常有价值。

**真正的稀疏向量：** 当前 Sparse 检索基于 Qdrant MatchText（非标准 BM25），对长文档的词频统计不够精确。计划引入 SPLADE 或 BM25 稀疏向量作为独立检索通道，结合 Qdrant 的 Named Vectors 功能（同一个 Point 存储 Dense + Sparse 两个向量），提升关键词检索的精度。这将使“混合检索”从“全文索引发的检索”进化为“真正的稀疏向量检索”。

**多轮对话感知改写：** 当前历史对话仅参与 LLM 生成阶段的 prompt 构建，未参与检索阶段的查询改写。计划将历史对话引入改写环节，解决“它的性能如何”类代词指代问题——当上一轮讨论了“水下蓝绿光 LD”，当前问题中的“它”应当被解析为该设备，并将解析后的完整问题用于检索。这将显著提升多轮对话场景下的检索精度。
